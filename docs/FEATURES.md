# Admin Toolkit for Salesforce — what every tool does

Admin Toolkit for Salesforce runs inside your browser and works through the Salesforce tabs you already have open — no separate login, no server of ours in between. Nothing about your data leaves your browser except to talk directly to your own Salesforce orgs. Anything that can change something in Salesforce shows you what it's about to do and asks first — an acknowledgement checkbox, and in Data Studio the org's name when the target is production. Where a tool reads the org back afterward, it says so; where it can only report what Salesforce answered, it says that instead.

## Toolkit (the popup)

### Flows
- Lists every flow in the org, grouped by name with each version, and shows a 🔗 mark when another flow calls it as a subflow. The search box narrows the list by flow name or API name. Read-only.
- 🗑 **Delete Selected** permanently removes the ticked flow versions. If any is Active it warns first and offers a backup; if paused runs are waiting on a version it offers to delete those too; if another flow still calls the one you're deleting, it shows you that calling flow and lets you delete it first, proceed anyway (Salesforce will refuse), or cancel. The final step needs an "I understand this is permanent" checkbox — Salesforce has no Recycle Bin for flow versions.
- ⬇ **Backup** downloads the selected version(s) as a file you could redeploy elsewhere, optionally including every flow it calls. 📥 **Restore** uploads a backup and redeploys it as a new Draft version — never turned on automatically; you activate it yourself in Flow Builder.
- Limit: a managed-package flow's contents can't be backed up (Salesforce hides them), and a flow another flow calls cannot be deleted until the caller is handled first.

- ⏻ Flow switches and ⚙ API versions show the flows as a hierarchy (2026-11-08): a flow's callees nested under it with a connector, from the dependency map; a subflow leaves its kind-group for its caller's; a shared subflow sits under its triggered caller.
- ⏻ Flow switches: a subflow chip ticks one level; when the chain goes deeper, "⇊ whole chain down N" / "⇈ every caller up N" name every flow in order and tick them all (2026-11-08).

### Dependencies (a view of the Flows page)
- A tree of every flow showing what calls what, a "what uses…" search for a field, object or value, 🧨 blast radius (what breaks if you touch this flow), and 🔗 chain (upstream and downstream, with loops detected). All read-only; an export downloads the same report as a file. Deleting a flow from here uses the same checks as the Flows tab, including a table of every flow that calls the one you're deleting.
- ⚙ **API versions** compares every flow's pinned API version to the org's own release. Pick flows and a target version, then acknowledge and confirm; it deploys a new version (activating it if the flow was Active) or rewrites a Draft in place, then re-reads the org and reports what changed and verified versus what Salesforce refused.
- Both views have a filter box above their list: type (or paste from a ticket) a flow name or API name and the list narrows as you type; a flow you ticked stays ticked when the filter hides it, the line under the box and the footer say how many ticked flows are hidden, and Enter with one flow left ticks it — so paste, tick, paste the next, tick, then one action for all of them.
- ⏻ **Flow switches** lists every flow in the org (2026-11-08): record-triggered flows by object, every other flow by its kind — scheduled, platform event, screen flows, autolaunched subflows, Process Builder, Omni-Channel routing, appointments and the rest, each named by its kind — with an On/Off state. A flow with no trigger of its own can be switched too; its confirmation line says what that breaks (every button, page, flow, Apex class or integration that starts it). After the dependency scan each row says which flows it calls and which call it, and a click on that chip ticks them too, so a subflow goes off with its caller. A record-triggered flow on a packaged object whose label does not come back is grouped under the object's API name. Turning flows off requires acknowledging and confirming, and warns automation stops for everyone and records created while off aren't processed retroactively; it re-reads the org afterward and remembers which version was active so turning back on can restore it — or says honestly it can't if there's no record of it.
- Limit: this only knows what a flow's own saved metadata calls, not buttons, Apex, REST or scheduled starts; a managed flow's contents can't be searched.

### Debugger
- Pick a user and a debug profile (or build a custom one); **Start Trace** turns on Apex debug logging for that user for one hour, **Stop Trace** turns it off — both re-check with Salesforce rather than assuming the click worked.
- The log list refreshes automatically while tracing, can be searched across every log's full text, and two logs can be compared side by side. Opening a log shows a colour-coded, line-by-line view with automation analysis that flags repeated/looping flows or triggers and how close the transaction came to a governor limit.
- Copy or download a summary report, download the raw log file, and delete logs one at a time, in bulk, or everything older than 24 hours (larger deletes need a second click to confirm).
- Limit: a trace always lasts one hour before it needs restarting; the log list shows at most 200 logs at once; a very large log may be too big for the built-in viewer and needs the raw download instead.

### Lightning Pages
- Lists every Lightning page, grouped by type, with its assignment status. A Lightning page has no separate "active" switch in Salesforce — being assigned somewhere *is* what makes it active — so a record page reads "Active" or "Not assigned", and a page whose assignments could not be read reads "Unknown".
- The detail view of a record page shows every assignment it has: org default, app default, and app + record type + profile, for desktop or mobile. Adding one asks first, names the page it replaces in that slot, writes it, then re-reads the org to confirm it landed. Removing one works the same way. **Deactivate** removes every assignment the page has, each named before you confirm.
- **Clone** creates an unassigned copy of a page. Moving the original's assignments to the copy is a separate choice that you confirm, because the original then stops being shown.
- "Who sees what?" is an org-wide, read-only audit of every record page and how many users each assignment reaches. "What a user sees" picks one user and shows which page wins for a given object and why, following Salesforce's own precedence order — and says outright when something (like permission-set-based visibility) isn't part of this model.
- Limit: it reads and changes the assignments of **record pages** only; Home, App and other page types are activated in Lightning App Builder and are listed without a status. Standard or managed pages can't be changed here. Pages cannot be deleted here. An org default can be undone from History; an app or profile assignment is taken back on the page itself.

### Field Cleaner
- Not the Flows tab: Flows is about a flow's own versions; Field Cleaner is about one field wherever it appears, and touches a flow only as one of the things that mention the field.
- Pick an object and a field, and scan for everything that references it — flow versions, failed flow runs on those versions, permission sets, page layouts, Lightning pages, reports, and more — flagging what it can fix automatically versus what needs a person (Apex, validation rules). Read-only.
- 🗑 **Delete** on every 🔒 blocker (2026-11-07): the component is read in full first (the restore point), removed with a destructiveChanges deploy, re-read to prove it is gone; ↩ Undo in History or ↩ Restore points deploy it back as it was — validation rules, workflow rules/field updates/alerts/outbound messages, approval processes, sharing rules, matching rules, field sets, custom buttons, formula fields, scoping/restriction rules, Lightning pages, custom metadata records, Apex classes/triggers, Visualforce pages/components, LWC and Aura bundles (sources kept and redeployed). The four that are not components of their own get the same button their own way (2026-11-07, "צריך את כולם"): a duplicate rule (deleted only from this explicit button), the lead field mapping (only this field's line goes), a lookup filter (only the filter goes, the field stays — a deploy of the field without it; a Tooling PATCH is refused), a Process Builder process (every version, switched off first; Undo deploys the latest back, inactive). Production Apex deletes run the org's tests only when Salesforce demands it.
- The results come in two sections: 🔒 **what must be cleared before Salesforce deletes the field** and 👀 **other mentions** (the delete goes through, these break or lose the field afterwards). Which is which was settled live (2026-11-06, one fixture per reference type, each put to a real delete), not taken from the docs. Blockers: Apex classes and triggers, Visualforce pages and components, formula and roll-up fields (same object or across a relationship), validation rules (active), flows and Process Builder (active or draft), workflow rules (active or not), field updates, email alerts, outbound messages, matching rules (active or not), duplicate rules with a filter on the field (active or not), approval processes (active or not), criteria-based sharing rules, scoping and restriction rules (active or not), Lightning pages (a field component or a visibility rule), Lightning web components that import the field's schema, custom metadata records whose Field Definition points at the field, lookup filters, field sets, custom buttons, the lead field mapping (both sides), Lead/Case assignment, auto-response and escalation rules. Mentions: page layouts, list views, compact layouts, quick actions, reports, report types, email templates (text, Visualforce and Lightning), Paths (the Path stays active on a field that no longer exists), inactive validation rules, permission set and profile field access. Salesforce's own "Where is this used?" is not the blocker list: it names layouts, reports and text templates, which do not block, and misses matching, workflow, approval, sharing, LWC and duplicate rules, which do.
- The scan shows its progress (2026-11-08): one segment per leg, the step, the time left and the places found so far, under the cat.
- ✉️ **Email templates** (2026-11-08) — classic text / HTML, Lightning, Visualforce: 🔍 shows the subject, body, HTML and markup with the field's lines marked; ✂ takes every merge field that names the field out, ⇄ renames it inside them, ✎ edits the texts; restore point and History undo (through the EmailTemplate record).
- 📊 **List views, compact layouts, quick actions, inactive validation rules** (2026-11-08) — the 👀 mention kinds the engine knows get ✂ / ⇄ / ✎ / 🗑 like the blockers.
- ✎ **Edit before deploying** (2026-11-08) — every ✂ / ⇄ confirm carries a folded box with the proposed XML (or a code file's text); change it and the deploy sends your text, well-formed or the button stays off.
- The 🔒 gate (chips, Delete Field) sits above the lists; ⚡ Everything at once sits on the section card's header (2026-11-08).
- Works on a custom field of a **packaged (namespaced) object** the same way — live on DLRS's `dlrs__LookupChild__c` (2026-11-08); the admin needs field-level security on the field first, and the Replace bar says so when not.
- 💻 **Code** (2026-11-08): Apex class / trigger, Visualforce page / component, LWC and Aura bundles — 🔍 shows every file with the field's lines marked; ⇄ Replace renames the field's API name as a whole word in every file (each changed file's diff confirmed first); ✎ Edit code is an editor per file, deployed back as the whole component; restore point and History undo. ✂ is not offered on code. A production org's Apex tests run when Salesforce asks for them.
- 👥 **Duplicate rules** have ✂ / ⇄ / ✎ like every other declarative kind (2026-11-08) — the owner's own click with the diff and a restore point; nothing switches a duplicate rule off or edits one behind a deployment.
- 🔒 **The blockers box** under the results: one header, one chip per kind (click → its group; the tooltip says its ways), one sentence about the ways; the count follows every fix.
- ⚡ **Everything at once** and the group "… all N" buttons cover every kind with a way (⇄ everywhere, ✂ where the kind can lose the field); a Remove walk names what it left out.
- The results header folds into three remembered sections — The field's data · Look further than the index · Act on everything — each summarised in one line when folded.
- 🧭 **Whole-org text sweep** (2026-11-08): on request, the tool reads the org's own metadata as a whole (Metadata API describe → list → retrieve, a few hundred components a time) and greps every text file for the field's API name. Hits are listed by kind with component, file and line: 🔒 what must go or change before the delete, 👀 what will break or lose the field afterwards — including the kinds the scan never reads (search layouts, related-list columns, record-type picklist values, Aura markup, LWC HTML, templates, reports, dashboards, translations, permission sets, profiles, Experience pages, custom labels). The cost is stated first, a progress bar with the time left runs on the page, Stop keeps what was read; nothing is written. Not read: static resources, documents, content and site assets, settings, certificates, anything from an installed package.
- Every blocker has a scan leg: the dependency index returns the Apex, Visualforce, formula, validation-rule, flow, lookup-filter, field-set, button and scoping-rule references; the scan reads the rest itself — Lightning pages one by one, workflow rules, alerts and outbound messages through the Tooling API, matching rules and field updates by query, approval processes, sharing rules, duplicate rules, the lead mapping and Lead/Case rules through readMetadata, Lightning web component sources in one query, custom metadata records when the org has up to 300 of them (more is said, not read). A Process Builder process is listed under Flows and blocks like one, but is never rewritten here: its card points to Setup. A switch above the Scan button picks what to scan: 🔍 Everything, 🔒 What blocks the delete, or 👀 Other mentions. A scan that read less says what it left out; a blocker the index returned is never hidden from the Delete button, only from the list. The choice is remembered. Not read, and not a blocker: Aura markup, an LWC that names the field only in its HTML, search layouts, related-list columns, record-type picklist values, dependent-picklist settings, Experience Cloud pages, and any text that holds the field's name. Not readable: territory rules and managed packages.
- A flow is shown as one card that says what will happen to each of its versions, and afterwards what happened: which version is active now and which were deleted.
- It removes what it safely can: deletes inactive flow versions (offering a backup first); a flow that runs on the field has two buttons on its card: **Remove · flow keeps running** creates a new active version with the reference removed, verifies it's active, then removes the old one; **Delete versions · flow off** switches the flow off and deletes the active version with the rest. The confirmation shows the consequence of the way you picked before anything changes. It can also remove just the one piece of a flow's own definition that references the field. Either way keeps a restore point of every version that goes, and the change can be undone from History: the version that was active comes back as the active version, numbered anew; the other deleted versions stay under ↩ Restore points below the results.
- **Replace it with another field** (optional step 3): pick a field of the same type on the same object and every item gets a second button — ⇄ Replace *moves* its reference to the new field, ✂ Remove takes it out, and you choose per item. With Replace, a flow gets a new active version that uses the new field — nothing else to choose — and keeps its logic; layouts and Lightning pages keep the slot, reports keep the column. Only references known to belong to this object's field are moved; a same-named field on another object is left alone and named. 🔑 Copy access gives the new field the same profile and permission-set access the old one has (only ever adding). 📦 Stored values compares the two fields on request and copies the old field's values into the new one — filling empty fields by default, overwriting only if you tick it, never touching the old field, and re-reading the records to confirm.
- 🕐 **Deprecate first** renames the field's label and description to flag it and strips access, without deleting anything — fully reversible. 🗑 **Delete Field**, once everything else is cleared, deletes the field (recoverable for a short window, then gone for good); you can back up its current values to a CSV first.
- **📊 Scan the reports** (on request): reports normally come from Salesforce's dependency index, which in some orgs lists none. This button reads every report you can open and finds the ones that use the field; it states the cost first (one API call per report), shows a live count and can be stopped. The reports it finds can be fixed like any other row.
- **📑 Report types**: every custom report type in the org is read (the dependency index does not list them) and the one with the field's column gets the same two buttons — ✂ Remove takes the column out (a section left with no columns goes with it), ⇄ Replace points it at the new field in place (when the new field is already a column, the old one is removed instead; a column may appear once). A restore point is saved first and ↩ Undo redeploys it; the change is verified by reading the type back. A report built on the type loses the column, so the reports listed above come first. A managed package's report type is listed and left to Setup.
- Limit: reports that only other people can open are not read by the report scan. Some references, like criteria-based sharing rules, can't be scanned by Salesforce's API at all, and the tool says so; picklist *values* are handled by Picklist Manager, not here.

### Copy Permissions
- Pick a source user and a target user, then choose what to copy: profile, role, permission sets, permission set groups, public groups, individual user permissions, and locale/timezone. Anything already matching is shown as such, so you don't overwrite it.
- Every planned change is listed and requires a checkbox before it writes anything; a profile or role change replaces the old one, but everything else only adds access — nothing is removed from the target user. It reports Salesforce's answer for each operation — what was assigned, what was refused and why.
- Limit: a permission set whose license doesn't match the target user's is shown but never force-assigned.

### Flow Access
- Pick one or more flows and one or more permission sets, see how many already have access, and grant them all in one action.
- It lists exactly what will be granted before writing (this always deploys a small metadata package, since a plain API write doesn't actually create this kind of access), then reloads the access list from the org so you can see the grant in place.
- Limit: this only grants access, with no revoke button; it covers screen and autolaunched flows, not record-triggered or scheduled flows; and it works with permission sets only, not permission set groups.

## Data Studio

### Connected Orgs
- Shows every Salesforce org you currently have open in a tab (and any you've had open before), with a connected / not-open status — no separate login, it rides your existing browser session.
- You can rename an org's label, forget an org the tool remembers, lock an org so nothing in the extension can write to it, and 🛑 **Guard as production** — treat any org as if it were production everywhere (typed confirmations, no hard deletes), even if Salesforce reports it as a sandbox. All of this is local to the extension; none of it touches Salesforce.
- Limit: a closed org can't have its real type (sandbox, production, trial) re-checked until you open it again.

### Data Deployment
- The matching section (Pick records › Matching, and the ✏ of a parent or a tree card) reads in layers: the key in one sentence on top with 🧪 / 💡, the strategy and fields, Advanced folded (normalize · most specific first), the suggestions as a table with the grade under each row (2026-11-08).
- The ⏸ pause panel is three tabs — Flows · Validation rules · Duplicate rules — each shown only when its option is on, with a one-sentence explanation, the objects this run writes and their items, all / none per object (2026-11-08).
- ▸ record shows the **Owner** right under Record Type (2026-11-08): the source owner by name, the default the run would write said in words, and a search over the target's active users and the queues that take the object (only where it can be queue-owned); a pick is written as OwnerId after the engine's own owner mapping.
- Build a reusable deployment — which object and related child records to move, and which field identifies a matching record between two orgs — from a template or from scratch, and import or export it as a file to share with a teammate (no passwords or org-specific record IDs travel with it).
- Opening a deployment goes to the 🚀 **Deploy** page, which scans both orgs and sorts every record into 🔴 Insert (missing from target), 🟡 Changed (differs), 🔵 only in target, 🟢 Synced, or ⚠ Needs a decision — nothing is ticked for you. ⚠ Needs a decision holds records whose match key both orgs hold more than once: the scan never guesses which copy is which; for each copy you say which target record it is, or that it is not there yet — one name at a time if you like; each answer is remembered at once and both orgs are read again when you ask. The tab never deletes: a left-over duplicate then shows under 🔵 only in target, where you can tick it for deletion. Lookups inside the same deployment connect automatically after insert; lookups outside it are matched by name, and you can hand-pick the right target record when a match is ambiguous or would land empty. Where a name exists more than once in ONE org, 🔀 **Merge these N into one** on that side makes it one record: the copies are read live and listed as rows (what tells each apart, its dates, how many fields it has filled; oldest / newest / most filled; the fullest ticked for you), you choose the record that stays and, for every writable field that differs, the value it keeps from the field's distinct values — each with the copies that hold it, a lookup shown by name — or one you type (the record that stays keeps its own unless you tick otherwise); after the shared confirmation the chosen values are written to it, the copies are merged into it — Salesforce's own merge for Accounts, Contacts, Leads and Cases (everything under the copies moves with it); for other objects each child relationship is moved and re-counted before a copy is deleted — and both orgs are read again. A merge cannot be undone by the Toolkit: the copies are in the Recycle Bin, but restoring them does not take back what moved; the dialog, the confirmation and the History entry say so.
- **🧾 Activity** (top bar of both the Toolkit and Data Studio) — the one place for everything either made: grouped by day and then by the tool or deployment, with a search, an app filter and ⬇ Export all. Every line carries its actions. In Data Studio: fix (▶ Continue, ↻ Retry failed), undo (↩ Roll back, 📋 Which records, ↩ Undo of a tool's change), open (🚀 Deploy, ✏ Profile), report (⬇). In the Toolkit: ↩ Undo and ⬇ Report of a tool's change; a deployment is handled from Data Studio's Activity. "details" on a deployment group opens the full History cards (per-object counts, the failed records by name).
- **▸ record** — on every Insert and Changed row, one editor for the values and the lookups, and for every ticked record of a list at once: the whole record, field by field, with the value it is written with. For one record every box holds that value (the source's unless you change it) and every change is saved as you type, so closing the dialog or the tab loses nothing; ✕ on a row goes back to the source's value, ∅ writes the field empty, and the footer says how many values are changed. If the record could not be read from the source, the dialog says so instead of showing an empty record. Type a value to write it instead of the source's (∅ writes the field empty), pick a lookup's target record from the target org in the same dialog. Saved on the deployment per target org; ▶ Deploy writes them (insert or update) and the run log says how many. The source is not changed, so after the run the record differs from its source until the orgs agree. A field the PII policy covers keeps its masked value.
- ✓ **Your ticks are remembered** — per deployment and target org, through a refresh, a run, a switch to another deployment and a closed tab. After every scan the page puts back each tick whose record is still in the list it was ticked in; a record that is in the target by now, or gone, is dropped and the page says how many came back and how many were dropped. A child object not read yet keeps its ticks until it is. Nothing is stored on disk in counts-only mode (the ticks then last for the session).
- 🪪 **Identity field** (the Deploy page's "Identity field" button): one small field, `SFTK_ID__c`, that stores on each target record the Id of the source record it came from. The table says per object whether each org has it and how many matched pairs the scan found; you create it in the target (and in the source, so the identity travels on) with one metadata deploy per org, plus a permission set so you can see it; **Stamp** writes the source Id onto the records the scan already matched — once — and from then on they match exactly, whatever their names do. Records a deployment creates are stamped as they are written. The stamp is in History with an undo.
- 🎭 **PII treatments** (the builder's Suggest PII treatments button, and 🎭 on every row of Fields & mapping): seed a sandbox from a Full Copy without the real people in it. Suggest reads every object's fields, its compliance classification and 200 real rows, and proposes a treatment per field from what the values look like; each row shows two real values and what they become, and you change the treatment per row. Treatments fabricate values that look real and pass validation — a name that is a name (Hebrew stays Hebrew), an e-mail made from the fabricated name on a .invalid domain the Contacts of one Account share, a phone in the same shape (US numbers on 555-01xx), a Luhn-valid card with the last four kept, an IBAN with its check digits, an Israeli ID with its check digit, an SSN in the never-issued area, a street, a date moved 1–180 days, free text with the e-mails, phones, cards and IDs inside it replaced — or a pseudonym (a hash), or empty. Every fake derives from a hash of the real value with a key kept on this PC: the same value always becomes the same fake, so joins, match keys and re-seeds survive; the source org is never changed. After the write the run reads a sample back and says whether anything still looks like PII outside the fields the policy fabricates. Wording everywhere: fabricated or pseudonymized — a shape-valid fake can coincide with someone's real number where a country reserves no test range, and each treatment says so.
- A **Duplicate rules** setting decides whether the target's own duplicate-detection can block a record (Respect) or is bypassed (Bypass) — bypassing forces the run onto the slower Collections API rather than Bulk API 2.0, since Bulk can't skip duplicate rules at all. A separate Engine setting picks between quick Collections calls and one big Bulk job for large volumes. The page says it as you choose: with Bulk chosen, batch size and threads disappear (Bulk splits the job itself) and a line says the target's duplicate rules run and cannot be bypassed; with Bulk and Bypass both chosen, a warning says the run is written through Collections calls after all.
- ↻ **Retry failed** re-opens a deployment with just the records that failed last time already ticked; History keeps Salesforce's answer for every record, and the run's own log names each refusal with Salesforce's text.
- **✓ Tick every insert** on the plan card ticks every record the target lacks in every object that was read, through the same parent rule as the per-tab "All" buttons; objects not read yet stay out, and so does a child whose parent is not on the way. Nothing is written until Deploy.
- A whole tree goes in one run: tick a grandchild (a line item on an Opportunity, a comment on a Case) and the parents it needs that are missing in the target come along automatically — the plan says how many were added — then everything is written parents first, each record linked to its new parent. If a parent is refused by Salesforce, its children are not inserted without it, and the run names them.
- ⏸ **The pause panel** (2026-11-08): with any pause option on, or Duplicate rules set to Bypass, the page lists under each object the run writes to what goes off in the target — record-triggered flows, validation rules, and the duplicate rules the bypass header passes — with a tick on every item and all / none per object. The unticked stay as they are and the confirmation says so ("left ON by your choice"); the duplicate-rule bypass is sent only for the objects ticked. Objects with nothing to switch are named in one line.
- ⏸ **Pause record-triggered flows** (an option next to ▶ Deploy, off by default): the page lists the active record-triggered flows on the deployment's objects in the target; the run's confirmation names them; they are switched off before the first write and back on at their exact versions as soon as the writes end — also when the run fails or is stopped. Records written while they are off are never processed by those flows. If the page closes mid-run, the Deploy page and Org health show which flows are still off, with a button to switch them on. Flows from installed packages cannot be switched and stay on.
- 🧪 **Dry run** (next to ▶ Deploy): a real write that Salesforce rolls back. The selected inserts go to the target in one transaction together with a record that always fails, so every validation rule, trigger, flow and duplicate rule runs on your real records — parents first, each child linked to its parent — and nothing is kept. The live run view and History say, per object, how many would be written, how many Salesforce refused (with its own error and the values sent; the record opens in the source org) and how many were not checked because their parent would be refused. The first 200 records of each object; deletes, updates and relinks are not part of it; ⏸ pauses are not applied; 🔗 lookups connected after insert and 📎 files are not checked. The selections stay for the ▶ Deploy that follows.
- ⏸ **Pause** on the live run view stops the run after the batch in flight — nothing is ever half-written. History shows "⏸ paused" with how far it got and offers ▶ **Continue**, which reopens the deployment with the records the run did not reach ticked again; records written before the pause are left alone. Closing the tab (or the X of the Chrome tab) while a run is on: the browser asks first; if you leave, the run stops after the batch in flight and the next Data Studio page says so once, with how far it got — a 🔍 Scan then lists what is still to deploy.
- Limit: a very large bucket is shown a page at a time, so a huge object can need more than one pass.

### All open orgs
- Pick one source org and every other org open in Chrome becomes a column; for every saved deployment you then see, at a glance, how far each org has drifted (missing, changed, or only-in-target counts) without opening each one individually. One Scan reads every deployment against every open org; opening a cell takes you straight to the 🚀 Deploy page for that pair to fix it. Nothing is crowned or remembered as "the" source: changing it here only changes which org the columns are measured from, and moves or rescans nothing.
- A record that looks like a duplicate of another is never auto-matched — it's flagged for you to pair by hand instead.
- 🔗 **Pair records by hand** (the Deploy page's "Match review"): the source records the scan found no match for on the left, the unmatched target records on the right, ranked by how alike the names are — the best of the start they share, the letter pairs in common and the words in common, the three shown on hover and the method explained in the dialog. Both records open; a pair is remembered for the target org and used on every scan (the record then shows under Changed or Synced instead of Insert); a pair made in the dialog can be taken back, and the remembered pairs of an org can be forgotten at once.
- Limit: this page only checks a deployment's top-level object, not its child records — check those directly on the Deploy page.

### History
- A log of every past deployment: the org pair, per-object counts (created, updated, deleted, failed), and a status of success, partial, or failed. Filter by status or deployment, and export any run — or all of them — as CSV or JSON.
- ↩ **Roll back**, launched from a run's card, undoes it: acknowledging and confirming (and typing the org's name for production) deletes what the run created and restores what it overwrote to its prior values, then re-reads the target and only reports "verified" for what it actually confirmed gone or restored.
- A change made by a Toolkit tool — a flow switched off or moved to a new API version, a permission copied, a Lightning page assigned, a field reference replaced — is listed in that tool, not here: while the tool is open its **History** button shows what was written, what the org showed afterwards, and ↩ Undo where the change can be taken back (Field Cleaner also lists it under its results). Data Studio’s History says how many such changes there are and opens each tool on its list.
- Limit: a rollback cannot undo automation that already ran because of the original write — emails already sent, records other flows or triggers created, or owner changes all stay as they are; hard-deleted records can't come back; and only the most recent runs keep enough information to be rolled back at all.

### Org Compare
- Pick two orgs and any objects, standard or custom, and see a record-count difference for each — how many exist in both, are missing from the target, or exist only in the target — matched by name, an external ID, or a field you choose. Read-only; 🚀 Deploy next to any row jumps straight to a scoped deployment for that object.
- Limit: this compares a whole object at once, not just the records a particular deployment cares about, so its numbers won't match a deployment's own scan of the same object.

### Org health
- One org at a time, one card per finding, most with a button into the tool that fixes it: licence types at their cap, active users who have not logged in for 90 days (integration users left out), flows switched off with ⏻ Flow switches and still off, your own flows three or more releases below the org's release, Lightning pages assigned to nobody, picklists that differ between your open orgs (for the object you name), and custom fields on an object that no record fills and nothing references.
- Nothing is read until you press Check or Check all; each card shows its API cost first, and Check all shows the org's remaining daily API budget. Answers are kept on this PC per org with the time they were checked.
- A check that could not read everything says so — "could not be checked", "NOT an all-clear" — and never shows a green result for something it did not read.
- Limit: the unused-fields card relies on the Tooling API's dependency index (a beta object), which does not reliably return reports, list views or Lightning pages the way Setup's own "Where is this used?" does, so its list is candidates to confirm in Field Cleaner before deleting anything.

### Schema View (Labs)
- An early preview: a visual map of how an org's objects relate to each other, optionally layered with which flows touch which objects, plus an on-demand overlay comparing that map against a second org. Read-only.
- Limit: an early preview that may not be fully reliable yet; a large org is capped to a portion of its objects unless you name the rest yourself.

### Field Audit (Labs)
- An early preview: ranks a chosen object's custom fields by how safe they'd likely be to delete — fill rate, who can see the field, how recently it changed, and how many other things depend on it — and can compare fill rates for the same field across your open orgs. Read-only; actually removing a field still happens in Field Cleaner.
- Limit: an early preview where a blank result on screen means "not measured," not "safe to delete" — it says so directly.

## Not in the public build yet

These tools exist and stay in the repository and the developer build. They were taken out of the
first public release (2026-10-03 and 2026-10-05, the owner's choice tool by tool) to keep it to
what has been used end to end; each returns as its own release. The in-app guide must not render
this section.

### Picklist Manager
- In a single org: every value with its active state, usage count and record types, plus a wizard for deactivating or removing a value that first checks flows and validation rules mentioning it by name (an honest, partial check stating how many it actually scanned) before letting you remap or clear the records that hold it.
- Comparing across orgs: a matrix of every value's state per org and 🔄 **Sync from source** to bring targets in line — adding missing values, deactivating what's gone, and aligning labels, record types and the default, with "also deactivate extra values the target has" left unticked by default. Bulk actions apply the same change across every ticked org at once. Standard picklists and shared (global) value sets can be viewed and edited too; 🔄 Sync from source cannot write them.
- Every write is confirmed first, production targets require typing the org's name, and any Run button waits until every org's automation check finishes before it becomes clickable.
- Limit: Salesforce's own API cannot truly delete a picklist value — the tool re-reads afterward and reports plainly that it was kept inactive instead, with the exact Setup path to delete it for good by hand.

### Sequences
- Chain several deployments into a **Sequence** that runs one after another against one org pair, so a later step can use records an earlier step just created. Running a Sequence lists every step and the stakes and requires an acknowledgement — plus the target org's name if it's production — before writing anything.

### Licenses
- Deactivate or reactivate one or more users at once (a dialog names everyone affected before you confirm). **Change License** reassigns a user's profile — which is how Salesforce ties a license — from a list grouped by license, and warns you to check a seat is free first.
- Reports success or failure per user from Salesforce's answer; after a deactivation it also tells you the user has moved to the Inactive filter, since the list shows active users by default.
- Limit: users are changed one at a time behind the scenes, so a large selection takes longer and partial failures are reported individually.

### Deploy Readiness
- Picks a source org and checks every other open org's schema against it before you migrate anything: missing or mismatched fields, picklist value gaps, missing record types, active validation and duplicate rules on the target, and org-level settings that can silently break a load (like State/Country picklists being on in one org and off in another). Only reads schema, never data.
- Every result states exactly which org pair and when it was checked; an inconclusive check is shown as unknown, never quietly counted as fine.
- Limit: this checks the *shape* of the data — fields, values, rules — not who can see or edit it.
